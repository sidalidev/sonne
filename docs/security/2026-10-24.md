# Internal security review, 24 Oct 2026

Versions reviewed: app 1.5.0, relay 1.1.0, web page of the same commit. Internal review, no external audit.

## Scope

Permissions, network, storage and cryptography of the Android app, the relay and the web page.

## Permissions

The release APK requests 17 permissions, listed in `docs/permissions.txt`, unchanged since 1.3.1. Each one has a single use: network (relay), foreground service and boot (staying reachable), notifications, full screen intent, vibration and Do Not Disturb (ringing), Bluetooth advertise, connect and scan with `neverForLocation` (Nearby), install packages (built-in updater), camera (QR scan, requested at scan time only). The CI now fails if a release build requests anything else.

Exported components: the launcher activity, and the boot receiver (system broadcasts). Another app can trigger the boot receiver directly, which only starts the keep-alive service: no impact.

## Network

- Release builds refuse cleartext traffic and `http://` relay addresses. The debug build allows them, for a local relay.
- Commands are signed (HMAC-SHA256), statuses are encrypted (AES-256-GCM, the chain id as associated data). The chain id never appears in a URL. The relay checks a proof derived from the key before accepting a phone.
- The relay writes nothing to disk; its log has counters and errors with 6 characters of id at most. Rate limits per id, per IP (IPv6 /64) and on open connections.
- The web proxy on the server logs every request (IP, time, path, size, no headers) for 7 days.
- No certificate pinning: the app trusts the system certificate store for the relay. Updates do not depend on it (see below).

## Storage

- The key is encrypted with an AES-256-GCM key from the Android Keystore, in device protected storage, so the phone still rings after a reboot before the first unlock. That Keystore key is not bound to user authentication, by design.
- Other phones (My other phones) keep only derived keys, in credential protected storage, with a Keystore key that requires an unlocked device.
- Backups and device-to-device transfer exclude every storage area.
- The key screen and the add-a-phone screen set `FLAG_SECURE`; copied words are marked sensitive on the clipboard.

## Cryptography

128-bit key from `SecureRandom`, HKDF-SHA256 for every derived key, HMAC-SHA256, AES-256-GCM, BIP39 words with checksum. Shared test vectors (`docs/VECTEURS.json`) are checked by the JVM tests, the relay tests and an independent WebCrypto test. In the browser, derived keys are non-exportable WebCrypto keys in IndexedDB. Updates are checked by SHA-256, package name, version code and signing certificate, against both the announcement and the installed app, before Android asks the user.

## Findings

1. No way to erase everything from the app. **Fixed in 1.5.0**: Erase everything (About) destroys every Keystore key of the app, then clears all its data and closes it.
2. The signing certificate could not be checked from the app. **Fixed in 1.5.0**: About shows the fingerprint read from the installed package; the full value is in `SECURITY.md`.
3. What the relay and the server see was not written down for users. **Fixed in 1.5.0**: What leaves your device, `PRIVACY.md`, `docs/THREAT_MODEL.md`.
4. Nothing prevented a release from gaining a permission. **Fixed in 1.5.0**: `docs/permissions.txt`, checked in CI and by `tools/release-android.sh`.
5. Commands are signed but not encrypted: the relay sees the command type. Accepted and documented.
6. The web proxy keeps IP addresses for 7 days. **Remains**: log only failed requests, rotate after 3 days.
7. The key stays in memory for the life of the process once read. **Remains**: low impact, the process is private to the app.
8. Three early commits carry a personal e-mail address as author. **Remains**: rewrite the history before the repository becomes public.
9. The relay is Apache-2.0 licensed, like the rest of the repository. **Remains**: decide on AGPL for the relay before publishing.
